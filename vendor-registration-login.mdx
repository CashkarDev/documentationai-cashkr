## Overview

Vendor Registration and Login in the Vendor App covers how new vendors onboard with documents and OTP, and how approved vendors access their accounts with OTP-based authentication.

The flow ensures only admin-approved vendors can log in, with all registration data and documents synced to the Admin Panel for review.

## Prerequisites

Vendors must have specific information and access ready before completing registration or login.

<Callout kind="info" collapsed="false">
  Registration and login both rely on OTP sent to the vendor's phone number. The phone number must be reachable during the flow.
</Callout>

- **For registration**

  - Valid mobile number that the vendor can access during OTP verification

  - Required business or identity documents in supported formats (for upload)

  - Basic business details (name, address, vendor category, etc.)

- **For login**

  - Phone number that is already registered and admin-approved in the Vendor App

  - Access to that phone to receive and read the OTP

## What happens after registration

After OTP verification, registration is not immediately active. The system creates a registration record and sends vendor details and documents to the Admin Panel.

Admin reviews the registration, sets the correct vendor type, and either approves or rejects the vendor. Until the admin approves, the vendor remains in a **pending** state and cannot log in.

When the admin approves the vendor, the account status changes to **active**, and the vendor can log in using the OTP-based login flow.

## System logic

This section summarizes the backend behavior that controls vendor access and security.

- **OTP validation**

  - Backend authentication service generates and validates OTPs for both registration and login.

  - The app must treat OTP verification as mandatory before sending any registration for approval or creating any login session.

- **Admin approval gating**

  - System marks vendors as **pending**, **approved**, or **rejected/inactive** based on admin decisions.

  - Only vendors with an **approved** status can successfully log in, even if OTP verification passes.

- **Session token storage**

  - After successful login, the backend issues a session token.

  - The Vendor App stores this token and sends it with subsequent requests until the vendor logs out or the token expires.

## Connections with Admin Panel

Vendor registration and login tightly integrate with the Admin Panel workflow.

- Registration requests and uploaded documents sync to the Admin Panel **Vendor Approval** section.

- Admin uses that section to:

  - Review vendor documents and details

  - Set or update the **vendor type**

  - Approve, reject, or deactivate vendors

- Login behavior in the Vendor App checks the vendor status that is managed in the Admin Panel before completing authentication.

## Common states and errors

These are the most common user-visible states and error conditions in the vendor registration and login journey.

- **Invalid phone number**

  - Triggered when the phone number format is wrong or fails basic validation.

  - Show a clear message to re-enter a valid phone number before sending OTP.

- **Incorrect OTP**

  - Happens when the entered OTP does not match the one generated by the backend.

  - Keep the vendor on the same screen and allow limited retries with an appropriate error message.

- **Expired OTP**

  - Occurs when an OTP is entered after its validity window has passed.

  - Prompt the vendor to request a new OTP and inform them that the previous OTP has expired.

- **Pending approval**

  - Vendor has completed registration and OTP verification, but admin has not yet approved the account.

  - During login, show a **pending approval** message instead of allowing access.

- **Rejected or inactive vendor**

  - Admin may reject the registration or later mark the vendor as inactive.

  - Login attempts should fail with a message indicating that the account is not active and contact support or admin.

<Callout kind="info" collapsed="false">
  Back-end logic must always apply the admin status check on every login, not only on first login, so deactivated vendors lose access immediately.
</Callout>

## Developer and tester notes

<Callout kind="tip" collapsed="false">
  Use fixed test phone numbers and OTP bypass hooks only in non-production environments. Verify that admin approval status always controls login, even when OTP is forced as valid in tests.
</Callout>

- Verify that:

  - Registration cannot proceed to admin approval without successful OTP verification.

  - Login fails for vendors whose status is not **approved**, even when OTP is correct.

  - Vendor type is only set from the Admin Panel and never editable from the Vendor App.

- Test flows:

  - New registration end-to-end, from OTP verification to admin approval and first login.

  - Re-login with an approved vendor after token expiry or logout.

  - Login attempts for **pending**, **rejected**, and **inactive** vendors.

  - Session token invalidation on logout and on manual deactivation from the Admin Panel.
