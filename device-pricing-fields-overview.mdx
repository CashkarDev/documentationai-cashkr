## Overview

Device evaluation responses include multiple price-related fields that represent different stages of the pricing workflow. Each field tracks how a device moves from base catalog price to final approved or requoted price.

## At a glance: pricing lifecycle

Use this workflow to see how a device price evolves from catalog value to final payout in the evaluation and order flow.

<Steps>

<Step title="Start from catalog base price" icon="database">

The evaluation starts with the base or listed price for the device model as stored in your catalog.

- `price` is the maximum possible value for the device in perfect condition.
- No deductions for condition, accessories, or warranty have been applied yet.

</Step>

<Step title="Apply automatic evaluation logic" icon="code">

Next, the system runs the configured pricing strategy to adjust the base price based on the actual device details.

- `deviceGeneratedPrice` is calculated from `price` after applying all evaluation rules.
- Deductions cover condition issues, missing accessories, warranty changes, and other parameters.

</Step>

<Step title="Confirm final payout at order completion" icon="check-circle">

When the vendor completes the order, they confirm or adjust the automatically generated price.

- `deviceFinalPrice` records the final approved price at the time of order completion.
- Vendors usually set this after physically inspecting the device or otherwise confirming its condition.

</Step>

<Step title="Requote after new findings (optional)" icon="edit">

If a later inspection or reassessment changes the valuation, the vendor can requote the device.

- `deviceRequotePrice` stores the updated quote after the initial final price.
- Use this when the condition is better or worse than originally recorded, or when pricing rules trigger a reassessment.

</Step>

</Steps>

## Field reference

Use these tabs to see how each field behaves in the evaluation and approval process.

<Tabs>

<Tab title="price" icon="database">

<>

**What it is**

The base or listed price of the device model, typically fetched from your database or product catalog before any deductions. It represents the maximum possible price if the device is in perfect condition.

**When it is set**

Set at the start of the evaluation flow, before applying condition checks, missing accessories, warranty adjustments, or any other deductions.

**Example**

- Base listing for a specific mobile model in perfect condition: `price = 107000`

</>

</Tab>

<Tab title="deviceGeneratedPrice" icon="code">

<>

**What it is**

The evaluated price automatically generated by the system based on device condition, warranty, missing accessories, and other parameters.

**When it is set**

Calculated after running the evaluation strategy logic (for example, `mobilePriceEvaluation`, `laptopPriceEvaluation`, `tabletPriceEvaluation`, or `macPriceEvaluation`). All configured deductions are applied on top of the `price` value.

**Example**

- Base price: `107000`
- Total deductions for condition/accessories: `23800`
- System-evaluated price: `deviceGeneratedPrice = "83200"`

</>

</Tab>

<Tab title="deviceFinalPrice" icon="check-circle">

<>

**What it is**

The final price approved by the vendor after confirming or adjusting the automatically generated evaluation.

**When it is set**

Set at the time of order completion, usually after the vendor inspects the device in person (or otherwise confirms the assessed condition) and agrees to a final payout amount.

**Example**

- System-evaluated price: `deviceGeneratedPrice = 83200`
- Vendor confirms this price after inspection
- Final approved price: `deviceFinalPrice = 83200`

</>

</Tab>

<Tab title="deviceRequotePrice" icon="edit">

<>

**What it is**

The new quoted price if the device is re-evaluated after the initial final price, often due to updated findings during a later inspection.

**When it is set**

Set when a revaluation happens after the first approval step. This could be because the physical inspection reveals a better or worse condition than expected, or when pricing rules trigger a reassessment.

**Example**

- Initial final price: `deviceFinalPrice = 83200`
- Reinspection finds the screen is better than expected
- Updated quote: `deviceRequotePrice = 85000`

</>

</Tab>

</Tabs>

## Worked example

Consider a user selling a mobile device:

- Base price from catalog: `price = 107000`
- Device condition issues and missing accessories cause total deductions of `23800`
- System evaluates the device and sets: `deviceGeneratedPrice = 83200`

If the vendor confirms this price after physically inspecting the device:

- Final approved price: `deviceFinalPrice = 83200`

If a later reinspection finds the screen is in better condition than initially recorded:

- Updated quote after revaluation: `deviceRequotePrice = 85000`

## Quick summary

- **Initial catalog value → `price`**: Base model price with no deductions applied.
- **After automatic system evaluation → `deviceGeneratedPrice`**: Auto-calculated estimated price based on evaluation logic.
- **After vendor approval → `deviceFinalPrice`**: Confirmed price used to complete the order.
- **After revaluation (requote) → `deviceRequotePrice`**: Updated final price after a second assessment.
