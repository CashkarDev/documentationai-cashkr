<Update label="2026-08-19" description="Internal vendors can add rejected applicant numbers as agents" tags={["vendor-app", "admin-panel"]}>
## What changed

- Documented that **internal vendors** can add the phone number of a **rejected vendor applicant** as one of their agents. External vendors cannot.
- **Only the phone number is freed for reuse.** The applicant's registered email stays tied to the closed application and must not be reused on the agent record.
- The applicant is **not notified**, and there is no consent step. Knowledge of the capability is limited to internal vendors.
- Updated [Add Agents](/add-agents) with the eligibility rule, per-field reuse behaviour, error handling, and QA checks for the internal-vendor gate.
- Updated [New Vendors - B2C](/new-vendors---b2c) so the rejection step states this downstream effect — rejecting an application no longer just closes it.

<Callout kind="alert">
Two things to watch. The internal-vendor check must be enforced **server-side**, not only in the app, or any vendor could add these numbers by calling the API directly.

And the errors shown must stay generic. Naming a number or email as "rejected vendor application" would leak a third party's outcome and turn the agent form into a lookup tool for checking whether any given number applied and was refused.

Remaining open questions on audit linkage, duplicate claims across internal vendors, re-application, and time limits are listed on the Add Agents page.
</Callout>
</Update>

<Update label="2026-08-19" description="Dedicated DID Number documented" tags={["vendor-app", "admin-panel", "telephony"]}>
## What changed

- Documented the **Dedicated DID Number** feature for the first time. Admins assign a dedicated DID number to each vendor, and outbound calls from the Vendor App present that number to the customer instead of the vendor's personal mobile.
- Added three pages: the feature overview under Core Features, a Vendor App calling guide, and an Admin Panel management guide.
- Cross-linked from Call Disposition and Vendors - B2C so the feature is reachable from where people already work.

<Callout kind="alert">
This feature was live and integrated with Acefone but had **zero documentation coverage** — no page mentioned DID, call masking, or number provisioning, and Acefone was absent from the tools inventory.

Several behaviours remain unconfirmed and are listed as open questions on the feature page: inbound calls to the DID, the fallback when no DID is assigned, whether agents share the parent vendor's number, call recording and retention, and what happens to the number when a vendor goes on Hold. The fallback question matters most — a silent fallback to direct dialling would expose personal numbers without anyone noticing.
</Callout>
</Update>

<Update label="2026-08-19" description="API Reference rebuilt from the backend Postman export" tags={["api", "security"]}>
## What changed

- Imported 246 backend operations, split into nine domain modules instead of one flat list.
- Fixed the navigation path that pointed at a non-existent `api-reference/openapi.yaml`, which is why the API Reference tab had always rendered empty.
- Added a `bearerAuth` JWT security scheme. The source export had an empty `securitySchemes` block and 246 per-operation `security: []` overrides, so every endpoint would have rendered as requiring no authentication.
- Replaced the placeholder Authentication page with a real API Overview documenting the OTP-to-JWT flow.

## Removed from the import

- 32 operations belonging to Google Maps Platform and the Push Lap Growth affiliate service. They inherited the Cashkr staging server URL and would have rendered as Cashkr endpoints.
- Oversized response examples, one of which was 41 KB for a single endpoint.

<Callout kind="alert">
**Security note.** The source export contained 14 real JWTs as example values, along with employee names, work emails, a personal email address, customer phone numbers, and local filesystem paths from a developer machine. All were replaced with placeholders before import.

The tokens had expired, but a future export generated a week earlier would have committed working vendor and admin session tokens to Git. Add a secret-scanning step before any Postman export is committed.
</Callout>
</Update>
