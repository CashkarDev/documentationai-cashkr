## Overview

The price evaluation module computes a final device price based on physical, technical, and warranty conditions, using device-type-specific strategies and class data lookup tables.

<Callout kind="info" collapsed="false">

- All strategies start from a **base price** and apply **deductions** for issues and **additions** for laptop hardware upgrades. Deductions may be flat or percentage values and always resolve from `basePrice`.

- If a device is marked as **dead** (does not turn on), strategies immediately return the configured **deadPrice** from class data.

- After applying all deductions and additions, strategies perform a **floor check**. If the computed price is less than or equal to `0`, the strategy falls back to **deadPrice** (or `0` if deadPrice is not available).

</Callout>

Use this page as the backend reference for engineering and QA when validating evaluation flows, mappings, and edge cases.

## Data model and request contracts

### EvaluationRequest

`EvaluationRequest` is the payload structure received from the app or admin panel when triggering a price evaluation.

<ParamField body="deviceId" param-type="string" required="true" deprecated="false">
  Unique identifier of the selected device record in the device table.
</ParamField>

<ParamField body="price" param-type="number" required="true" deprecated="false">
  Base price of the device before applying any deductions or additions. Often comes from the device table and is passed into `basePrice`.
</ParamField>

<ParamField body="bodyCondition" param-type="string" required="false" deprecated="false">
  Body condition code, such as `B1` or `B2`. Used to look up a deduction amount in class data and passed through `resolveDeduction(classData[bodyCondition], basePrice)`.
</ParamField>

<ParamField body="screenCondition" param-type="string" required="false" deprecated="false">
  Screen condition code for mobile-style devices, typically `S1` to `S5` (for example, `S1` flawless, `S5` heavily damaged). Mobile-style strategies look up `classData[screenCondition]` and call `resolveDeduction(classData[screenCondition], basePrice)` to compute the deduction. The laptop strategy ignores this field and relies on `screenSize` instead.
</ParamField>

<ParamField body="screenSize" param-type="string" required="false" deprecated="false">
  Laptop screen size **code**, expected to be `S1` to `S4` per the laptop-size bands in the diagram (not a free-form inches label). The laptop strategy treats this as a size-based deduction by reading `classData[screenSize]` and calling `resolveDeduction(classData[screenSize], basePrice)`. Mobile-style strategies ignore this field.
</ParamField>

<ParamField body="isDeviceTurnedOn" param-type="boolean" required="true" deprecated="false">
  Indicates whether the device powers on. If `false`, strategies return the dead price without further checks or deductions.
</ParamField>

<ParamField body="physicalCondition" param-type="string[]" required="false" deprecated="false">
  Array of physical damage codes (for example, `P1`, `P3`). Each code maps to a deduction in class data and is applied using `resolveDeduction(classData[code], basePrice)`.
</ParamField>

<ParamField body="processorId" param-type="string" required="false" deprecated="false">
  Identifier of the selected laptop processor, used to fetch an additive value from the processor table and add it directly to `finalPrice`.
</ParamField>

<ParamField body="ramId" param-type="string" required="false" deprecated="false">
  Identifier of the selected laptop RAM configuration, used to fetch an additive value from the RAM table and add it directly to `finalPrice`.
</ParamField>

<ParamField body="storageId" param-type="string" required="false" deprecated="false">
  Identifier of the selected laptop storage configuration, used to fetch an additive value from the storage table and add it directly to `finalPrice`.
</ParamField>

<ParamField body="technicalCondition" param-type="string[]" required="false" deprecated="false">
  Array of technical fault codes (for example, battery, Wi-Fi, mic issues such as `T1`). Each code maps to a deduction in class data and is applied using `resolveDeduction(classData[code], basePrice)`.
</ParamField>

<ParamField body="warrantyStatus" param-type="string" required="true" deprecated="false">
  Warranty status code, such as `W1`, `W2`, `W3`, or `W4`. Each code maps to a deduction in class data and is applied using `resolveDeduction(classData[warrantyStatus], basePrice)`.
</ParamField>

<ParamField body="accessories" param-type="string[]" required="true" deprecated="false">
  Array of accessory codes provided with the device (for example, `A1` to `A4` for bill, box, charger, other). Missing accessories are inferred by comparing against the full set; each missing accessory applies a deduction using `resolveDeduction(classData[code], basePrice)`.
</ParamField>

<ParamField body="deviceType" param-type="string" required="true" deprecated="false">
  Logical device type, such as `Mobile`, `Laptop`, `Tablet`, `Camera`, `Headphone`, `Console`, `Drone`, `TV`, `AC`, `Desktop`, `Mac`, or `Watch`. Used to select table mappings and strategy.
</ParamField>

### EvaluationParams

`EvaluationParams` is the internal structure passed into each evaluation strategy.

<ParamField body="classData" param-type="any" required="true" deprecated="false">
  Row from the class table that contains all deduction and dead price fields for the device class (for example, `deadPrice`, `W1`, `B1`, `S1`, `P1`, `T1`, `A1`). Individual values may be flat numbers, numeric strings, or percentage strings; strategies always pass them to `resolveDeduction(value, basePrice)` before subtracting.
</ParamField>

<ParamField body="basePrice" param-type="number" required="true" deprecated="false">
  Starting price and the reference for all percentage calculations, usually taken from `request.price` or directly from the device table.
</ParamField>

<ParamField body="request" param-type="EvaluationRequest" required="true" deprecated="false">
  The full incoming `EvaluationRequest`. Strategies read fields such as `warrantyStatus`, `bodyCondition`, `screenCondition`, `screenSize`, `technicalCondition`, `physicalCondition`, `accessories`, and hardware IDs from this object.
</ParamField>

### DeviceTableMap

`DeviceTableMap` describes how each logical device type maps to database tables and a specific evaluation strategy.

<ParamField body="tableName" param-type="string" required="true" deprecated="false">
  Prisma model name of the base device table (for example, `deviceMobiles`, `deviceLaptops`).
</ParamField>

<ParamField body="classTableName" param-type="string" required="true" deprecated="false">
  Prisma model name of the corresponding class table that stores deduction and dead price fields (for example, `classMobile`, `classLaptop`).
</ParamField>

<ParamField body="evaluationStrategy" param-type="(params) => Promise<number>" required="true" deprecated="false">
  Function reference for the strategy that computes the final price for this device type (for example, `mobilePriceEvaluation`, `laptopPriceEvaluation`).
</ParamField>

## Deduction value resolution

Use a single helper rule, `resolveDeduction(value, basePrice)`, everywhere you apply class-data-based deductions.

- Deductions in `classData` can be:

  - a **flat number** like `500`, or

  - a **numeric string** like `"500"` that should behave the same as a flat number, or

  - a **percentage string** like `"10%"`, always resolved against `basePrice`.

- When the value is a flat number or a numeric string, `resolveDeduction` returns that number directly.
- When the value is a percentage string, `resolveDeduction` computes the deduction as a percentage of `basePrice`, not of the running `finalPrice`.

In pseudo-code:

```ts
function resolveDeduction(value, basePrice) {
  if (typeof value === "number") {
    return value; // flat numeric deduction
  }

  if (typeof value === "string") {
    if (value.endsWith("%")) {
      const pct = Number(value.slice(0, -1));
      return (basePrice * pct) / 100; // percent of basePrice
    }

    const asNumber = Number(value);
    if (!Number.isNaN(asNumber)) {
      return asNumber; // numeric string treated as flat deduction
    }
  }

  return 0;
}
```

All deduction steps in both strategies conceptually call `resolveDeduction(classData[code], basePrice)`, so every percentage-based value always uses `basePrice` as the reference.

## Evaluation strategies

### Mobile-style strategy (`mobilePriceEvaluation`)

Used for `Mobile`, `Tablet`, `Camera`, `Headphone`, `Console`, `Drone`, `TV`, `AC`, `Desktop`, `Mac`, and `Watch`.

<Steps>
  <Step title="Dead device check" icon="alert-triangle" title-type="p">
    If `request.isDeviceTurnedOn` is `false`, return `classData.deadPrice` immediately (or `0` if deadPrice is not present) and skip all further logic.
  </Step>

  <Step title="Start from base price" icon="play-circle" title-type="p">
    Initialize `finalPrice` from `basePrice` in `EvaluationParams`. This is typically the frontend base price or device table price.
  </Step>

  <Step title="Apply warranty deduction" icon="settings" title-type="p">
    If `request.warrantyStatus` is present, read the matching value from `classData` using the warranty code key (for example, `classData["W3"]`), resolve it with `resolveDeduction(classData[request.warrantyStatus], basePrice)`, and subtract the result from `finalPrice`:

    ```ts
    const warrantyValue = classData[request.warrantyStatus];
    finalPrice -= resolveDeduction(warrantyValue, basePrice);
    ```
  </Step>

  <Step title="Apply body condition deduction" icon="settings" title-type="p">
    If `request.bodyCondition` is provided (for example, `B2`), read `classData[request.bodyCondition]`, resolve it with `resolveDeduction(classData[request.bodyCondition], basePrice)`, and subtract that resolved amount from `finalPrice`.
  </Step>

  <Step title="Apply screen condition deduction" icon="settings" title-type="p">
    If `request.screenCondition` is provided (for example, `S1` to `S5`), read `classData[request.screenCondition]`, resolve it with `resolveDeduction(classData[request.screenCondition], basePrice)`, and subtract the resolved amount from `finalPrice`.
  </Step>

  <Step title="Apply physical damage deductions" icon="settings" title-type="p">
    If `request.physicalCondition` contains one or more codes (for example, `["P1", "P3"]`), iterate through the array, resolve each `classData[code]` via `resolveDeduction(classData[code], basePrice)`, and subtract the resolved amount from `finalPrice` for every code.
  </Step>

  <Step title="Apply technical fault deductions" icon="settings" title-type="p">
    If `request.technicalCondition` contains one or more codes (for example, `["T1"]`), iterate through the array, resolve each `classData[code]` via `resolveDeduction(classData[code], basePrice)`, and subtract the resolved amount from `finalPrice` for every code.
  </Step>

  <Step title="Apply missing accessory deductions" icon="settings" title-type="p">
    Derive the full accessory set for the class (for example, codes `A1`, `A2`, `A3`, `A4`). For each code that is **not** in `request.accessories`, resolve `classData[code]` with `resolveDeduction(classData[code], basePrice)` and subtract the resolved amount from `finalPrice`.
  </Step>

  <Step title="Final price fallback" icon="check-circle" title-type="p">
    If `finalPrice` is greater than `0`, return it. If `finalPrice` is less than or equal to `0`, return `classData.deadPrice` if available, otherwise return `0`.
  </Step>
</Steps>

### Laptop strategy (`laptopPriceEvaluation`)

Used for `Laptop` (and can be reused for similar form factors such as desktops if needed).

<Steps>
  <Step title="Dead device check" icon="alert-triangle" title-type="p">
    If `request.isDeviceTurnedOn` is `false`, return `classData.deadPrice` (or `0` if deadPrice is not present) and skip all further computations.
  </Step>

  <Step title="Start from base price" icon="play-circle" title-type="p">
    Initialize `finalPrice` with `basePrice` from `EvaluationParams`.
  </Step>

  <Step title="Apply warranty and cosmetic deductions" icon="settings" title-type="p">
    - If `request.warrantyStatus` is set, read `classData[request.warrantyStatus]`, resolve it with `resolveDeduction(classData[request.warrantyStatus], basePrice)`, and subtract the resolved amount from `finalPrice`.

    - If `request.bodyCondition` is provided, read `classData[request.bodyCondition]`, resolve it with `resolveDeduction(classData[request.bodyCondition], basePrice)`, and subtract the resolved amount from `finalPrice`.

    - For laptops, treat screen as **screen size code** rather than condition: if `request.screenSize` is provided, expect it to be one of `S1` to `S4`. Read `classData[request.screenSize]`, resolve it with `resolveDeduction(classData[request.screenSize], basePrice)`, and subtract the resolved amount from `finalPrice`. The laptop strategy does **not** use `request.screenCondition` for any calculation.
  </Step>

  <Step title="Apply physical and technical deductions" icon="settings" title-type="p">
    - For each code in `request.physicalCondition`, resolve `classData[code]` with `resolveDeduction(classData[code], basePrice)` and subtract the resolved amount from `finalPrice`.

    - For each code in `request.technicalCondition`, resolve `classData[code]` with `resolveDeduction(classData[code], basePrice)` and subtract the resolved amount from `finalPrice`.
  </Step>

  <Step title="Apply missing accessory deductions" icon="settings" title-type="p">
    Compare `request.accessories` against the configured accessory codes (`A1` to `A4`). For each missing accessory code, resolve `classData[code]` with `resolveDeduction(classData[code], basePrice)` and subtract the resolved amount from `finalPrice`.
  </Step>

  <Step title="Add hardware upgrades (processor, RAM, storage, optional graphic card)" icon="database" title-type="p">
    If `request.processorId`, `request.ramId`, or `request.storageId` are provided:

    - Fetch the matching processor, RAM, and storage records from their respective tables.

    - For each record found, add its numeric value (for example, `amount` or `priceDelta`) directly to `finalPrice` as an addition, without passing through `resolveDeduction`.

    These are **additions** and can offset earlier deductions.

    Optionally, you may also introduce a dedicated **graphic card** lookup table and field in an internal laptop evaluation context. If present, fetch the graphic card record and add its numeric value to `finalPrice` in the same way as processor, RAM, and storage.
  </Step>

  <Step title="Final price fallback" icon="check-circle" title-type="p">
    If `finalPrice` is greater than `0`, return it. If `finalPrice` is less than or equal to `0`, return `classData.deadPrice` if available, otherwise `0`.
  </Step>
</Steps>

<Callout kind="info">
  The **graphic card** add-on in the laptop logic is conceptual and optional. It only applies if you introduce a matching field or lookup table in your laptop evaluation strategy; it is not part of the current `EvaluationRequest` contract.
</Callout>

## Main controller: Evaluations(req, res)

`Evaluations(req, res)` is the Express controller that orchestrates validation, mapping, data fetching, and strategy execution.

<Steps>
  <Step title="Parse and validate request" icon="terminal" title-type="p">
    - Read the incoming JSON payload as an `EvaluationRequest`.

    - Based on `deviceType`, validate the payload with the appropriate Zod schema (for example, `LaptopEvaluationRequestSchema`, `MacEvaluationRequestSchema`, `MobileEvaluationRequestSchema`).

    - If validation fails, return a `400` response with `"Invalid data"`.
  </Step>

  <Step title="Resolve device mapping" icon="settings" title-type="p">
    Use `deviceType` to look up the entry in `deviceTableMap`. If there is no mapping for the given type, return a `400` response with `"Evaluation for &lt;type&gt; not yet supported"`.
  </Step>

  <Step title="Fetch device and class data" icon="database" title-type="p">
    - Query the base device table (for example, `deviceMobiles`) using `deviceId`.

    - Include or join the corresponding class table row (for example, `classMobile`) that contains `deadPrice`, warranty codes, condition codes, and accessory deductions.

    - If the device record is not found, return `404` with `"Device not found"`.

    - If the class data is missing, return `404` with `"Class data not found for &lt;type&gt;"`.
  </Step>

  <Step title="Compute final price" icon="code" title-type="p">
    Call the mapped evaluation strategy with `EvaluationParams`.

    <CodeGroup show-lines="true" tabs={[]}>
      ```ts
      const evaluationRequest = parsedBody;

      const { tableName, classTableName, evaluationStrategy } =
        deviceTableMap[evaluationRequest.deviceType];

      const device = await prisma[tableName].findUnique({
        where: { id: evaluationRequest.deviceId },
        include: { classData: true }, // actual relation name depends on schema
      });

      if (!device) {
        return res.status(404).json({
          success: false,
          message: "Device not found",
        });
      }

      if (!device.classData) {
        return res.status(404).json({
          success: false,
          message: `Class data not found for ${evaluationRequest.deviceType}`,
        });
      }

      const finalPrice = await evaluationStrategy({
        classData: device.classData,
        basePrice: evaluationRequest.price,
        request: evaluationRequest,
      });
      ```
    </CodeGroup>
  </Step>

  <Step title="Return response" icon="check-circle" title-type="p">
    On success, return a `200` response with a payload similar to:

    ```json
    {
      "success": true,
      "message": "Price evaluation successful",
      "data": {
        "deviceId": "mbl12345",
        "deviceType": "Laptop",
        "credit": "credit_value",
        "price": 39600
      }
    }
    ```

    Wrap the entire controller in a `try` or `try/catch` block and return a `500` response with `"Internal Server Error"` if any unhandled exception occurs.
  </Step>
</Steps>

## Error handling

The controller standardizes error responses for common cases:

- **Invalid schema**

  - Status: `400`

  - Message: `"Invalid data"`

  - Trigger: Zod validation fails for the chosen `deviceType` schema.

- **Unsupported device type**

  - Status: `400`

  - Message: `"Evaluation for &lt;type&gt; not yet supported"`

  - Trigger: `deviceType` not present in `deviceTableMap`.

- **Device not found**

  - Status: `404`

  - Message: `"Device not found"`

  - Trigger: No device record for the given `deviceId` in the mapped `tableName`.

- **Class data missing**

  - Status: `404`

  - Message: `"Class data not found for &lt;type&gt;"`

  - Trigger: Device is found but the associated class data row is missing.

- **Unexpected server error**

  - Status: `500`

  - Message: `"Internal Server Error"`

  - Trigger: Any unhandled runtime error, such as database failure or strategy exception.

## Extending the logic

To support a new device type using the same evaluation infrastructure:

<Steps>
  <Step title="Create Prisma models" icon="database" title-type="p">
    Add base and class table models for the new type. For example:

    - Base table: `deviceSmartTVs`

    - Class table: `classSmartTV`

    Ensure the class table exposes `deadPrice`, warranty codes, condition codes, and accessory fields similar to existing class tables, and that the deduction fields follow the `resolveDeduction` flat-or-percentage pattern (including numeric strings).
  </Step>

  <Step title="Implement evaluation strategy" icon="code" title-type="p">
    Create a new strategy function or reuse an existing one, depending on requirements.

    ```ts
    async function smartTVPriceEvaluation(
      params: EvaluationParams
    ): Promise<number> {
      // mirror mobilePriceEvaluation with resolveDeduction(classData[code], basePrice)
      // or customize as needed
    }
    ```
  </Step>

  <Step title="Update device table map" icon="settings" title-type="p">
    Register the new mapping entry so the controller can resolve tables and strategy.

    ```ts
    deviceTableMap.SmartTV = {
      tableName: "deviceSmartTVs",
      classTableName: "classSmartTV",
      evaluationStrategy: evaluationStrategies.smartTVPriceEvaluation,
    };
    ```
  </Step>

  <Step title="Add validation schema" icon="shield" title-type="p">
    Define and wire a Zod schema for the new type so that `Evaluations(req, res)` can validate payloads before execution.
  </Step>
</Steps>

## Worked examples

### Mobile example (deductions only)

Assume the following for a mobile device, and assume all mentioned class-data values **resolve to flat amounts** using `resolveDeduction` (they may be numbers or numeric strings):

- Base price: `₹20,000`

- Device turns on: `true`

- Warranty: `W3` → resolves to `₹800` deduction

- Body: `B2` → resolves to `₹500` deduction

- Screen condition: `S1` → resolves to `₹400` deduction

- Missing accessories: `A3`, `A4` → resolve to `₹600` total deduction

- Technical issue: `battery` (for example, `T1`) → resolves to `₹300` deduction

Price evolution:

1. Start: `₹20,000`
2. After warranty `W3`: `₹20,000 - 800 = ₹19,200`
3. After body `B2`: `₹19,200 - 500 = ₹18,700`
4. After screen `S1`: `₹18,700 - 400 = ₹18,300`
5. After missing `A3` and `A4`: `₹18,300 - 600 = ₹17,700`
6. After technical issue `T1`: `₹17,700 - 300 = ₹17,400`

Final evaluated price is `₹17,400`.\
Since this is greater than `0`, the strategy returns `₹17,400` instead of `deadPrice`.

If the cumulative resolved deductions had dropped the price below or equal to `0`, the strategy would have returned `deadPrice` from `classData` (for example, `₹500` or `₹1,000`).

### Laptop example (deductions and additions)

Assume the following for a laptop, and again assume all class-data values **resolve to flat amounts** via `resolveDeduction`:

- Base price: `₹40,000`

- Device turns on: `true`

- Warranty: `W2` → resolves to `₹1,000` deduction

- Screen size code: `S2` → resolves to `₹400` deduction from `classData["S2"]`

- Missing accessory: charger (`A1`) → resolves to `₹800` deduction

- RAM upgrade: `16GB` → `₹1,000` addition (from RAM table)

- SSD upgrade: `512GB` → `₹800` addition (from storage table)

Price evolution:

1. Start: `₹40,000`
2. After warranty `W2`: `₹40,000 - 1,000 = ₹39,000`
3. After screen size deduction `S2`: `₹39,000 - 400 = ₹38,600`
4. After missing charger `A1`: `₹38,600 - 800 = ₹37,800`
5. After RAM upgrade `16GB`: `₹37,800 + 1,000 = ₹38,800`
6. After SSD upgrade `512GB`: `₹38,800 + 800 = ₹39,600`

Final evaluated price is `₹39,600`.\
Because `39,600` is greater than `0`, the strategy returns this value and does not fall back to `deadPrice`.

## Summary formula

Across all strategies, the conceptual formula is:

```text
Final Price = Base Price - Total Deductions + Total Additions
```

Where:

- **Total Deductions** includes warranty, body, screen or screen-size, physical, technical, and missing accessory deductions, each computed as `resolveDeduction(classData[code], basePrice)` so that all percentages are based on `basePrice`.
- **Total Additions** currently covers laptop hardware upgrades (processor, RAM, storage, and optionally graphic card if configured) as direct numeric additions.

If the evaluated `Final Price` is less than or equal to `0`, the system returns:

```text
Fallback Price = deadPrice (from classData) or 0 if deadPrice is not defined
```
