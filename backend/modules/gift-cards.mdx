<Callout kind="tip">Gift card value = (Final, else Requote, else Generated) + BuyBack bonus, then the gift-card % on top, capped at ₹10,000. See [Device Price Lifecycle](/backend/device-price-lifecycle).</Callout>

## Purpose

Lets a customer take their device payout as an Amazon e-gift card (paymentType GiftCard) instead of Cash/UPI/Bank, with a bonus on top (fixed WOOHOO_GIFT_BONUS_BPS, e.g. 200 = +2%, else Woohoo's per-SKU corporateDiscounts). CashKr issues the card at order completion through Woohoo (Pine Labs/Qwikcilver) from its prepaid SVC balance; the vendor pays nothing in cash.

## Core Business Logic

1.  **Eligibility & quote.** Rollout allowlist WOOHOO_GIFT_ALLOWED_PHONES (empty = everyone). Base = deviceFinalPrice ?? deviceRequotePrice ?? deviceGeneratedPrice (+ influencer bonus and coupon discount when only the raw quote exists) + BuyBack bonus (giftCardAmount.ts). Bonus bps: WOOHOO_GIFT_BONUS_BPS if &gt; 0, else Woohoo corporateDiscounts for the SKU cached in Redis for 24 h, capped at 5000 bps. Face = round-to-rupee(base × (1 + rate)). Must be within ₹1–₹10,000 (RBI cap). payoutDisplay.ts / giftCardDisplay.ts add the same overlay for display in order lists, invoices and the vendor app.

2.  **Choosing GiftCard.** Customer picks paymentType = GiftCard at checkout (web) or the vendor sets it pre-completion via PATCH /order/:id/payment-method (pre-validated for cap + rollout). After completion the method is locked; a COMPLETE or PENDING GiftCardOrder blocks any switch (double-pay guard).

3.  **Issuance at completion** (masterLead.service.ts completeLead): if paymentType === "GiftCard": final + BuyBack bonus must be within the cap, else 409 "exceeds ₹10,000"; issueGiftCardForLeadSync → prepareGiftCardIssue (allowlist, base, bonus, cap, refNo idempotency, delivery address and state) → insert GiftCardOrder PENDING → Woohoo create order (timeout 35 s in prod, else 10 s). Inline COMPLETE → cards fetched → status COMPLETE, card number/PIN encrypted at rest, customer FCM push + GIFT_CARD_ISSUED email → order finalized. Not COMPLETE inline or timeout → order stays PENDING, lead stays InProgress with collection data saved, response giftCardStatus:"issuing", pendingPayout:true; vendor app polls /order/:id/giftcard-status. Provider rejection (e.g. invalid SKU) → order FAILED, 409 to vendor "switch to Cash/UPI/Bank".

4.  **Woohoo integration.** OAuth2 bearer token cached in Redis (6 days, refreshed once on rejection); every request is HMAC-signed as Woohoo requires. client.ts wraps axios into WoohooApiError / WoohooTimeoutError (timeouts route to the pending path).

5.  **Catalog.** catalog.ts exposes the Woohoo catalog endpoints. Only getProductBySku is used in src (bonus rate); listing calls are used by scripts. There is no catalog → DB sync.

6.  **Recovery / reconciliation** (recovery.ts). resolveByRefNo queries the order status; "order not available" while within the deadline → pending_processing, after the deadline → never_created_retry_safe; COMPLETE → success (via 'status_poll'); other status after deadline → failed_refund_required. reconcileStuckPendingOrders(\{floorMinutes:1, deadlineMinutes:3\}) polls PENDING orders every run. pollGiftCardIssueStatus (vendor poll) applies the same 3-minute deadline and finalizes the lead on success; the vendor switches to Cash/UPI/Bank on failure.

7.  **Customer access.** GET /api/v1/lead/:id/giftcard decrypts and returns the card only to the owning customer; admin endpoints never expose it.

## Status / State Machine

GiftCardOrder.status: PENDING (created) → COMPLETE (card issued, via inline or status_poll) \| FAILED (provider rejection, or never-created after deadline) \| REFUND_REQUIRED (provider says not complete after deadline). PROCESSING, TIMEOUT_RECOVERY, CANCELLED, REFUNDED are defined but never written in src/. recoveryOutcome ∈ inline \| status_poll \| pending_processing \| failed_refund_required \| never_created_retry_safe. Lead-side: giftCardStatus issued \| issuing \| failed.

## Validations & Rules

Cap ₹1–₹10,000 on the grossed-up face; one card per lead via unique refNo; allowlist gate at quote and issuance; admin limit ≤ 100 and status validated against the enum; max 5000 bps; whole-rupee faces; card secrets encrypted at rest; email/phone normalized to +91XXXXXXXXXX.
